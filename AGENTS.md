# Agent Development Guidelines

Guidelines for AI agents and human contributors working on the **`hbc`** repository.

## 1. Tech Stack

- **Core Engine**: Pure TypeScript Headless Game Engine (`src/engine/`)
- **Framework**: React 19 + Vite
- **Language**: TypeScript (strict mode, native compiler `@typescript/native`)
- **UI & Styling**: TailwindCSS v4
- **Testing**: Vitest
- **Code Quality**: ESLint (`strictTypeChecked`, `stylisticTypeChecked`), Prettier, Knip

## 2. Architectural Conventions

### Headless Engine First

- Absolutely **NO** DOM, Canvas, React, or UI framework dependencies inside `src/engine/`.
- All game mechanics must be tested in pure Node/TypeScript execution environments without browser mocks.

### Pure State Transitions & Event Sourcing

- The core engine function must be deterministic and pure:
  ```ts
  dispatch(state: GameState, action: Action): { nextState: GameState; events: GameEvent[] }
  ```
- `nextState` must be immutable (no direct in-place state mutation).
- `events` provides an ordered sequence of event triggers for VFX, audio, and visual playback.

### Information Security & Fog of War

- Hidden skills (`WALL`, `BOMB`, `COUNTER`, unrevealed `PIERCE`) must remain confidential.
- Client applications must only receive sanitized states generated by:
  ```ts
  sanitizeForViewer(state: GameState, viewerPlayerId: number): MaskedGameState
  ```
- An opponent should never be able to inspect unrevealed enemy skills via DOM or network inspection. Teammates can see unrevealed skills.

### React Compiler

- Automatic fine-grained memoization is enabled via `@vitejs/plugin-react` (`reactCompilerPreset`) and `@rolldown/plugin-babel`.
- Do not write manual `useMemo`, `useCallback`, or `React.memo` unless handling non-compiler edge cases.
- Follow `eslint-plugin-react-hooks`'s `recommended-latest` rules.

### TailwindCSS v4 Styling

- Tailwind CSS v4 `@theme` in `src/global.css` is the source of truth for design tokens.
- Use Tailwind CSS v4 canonical class syntax. Run `npm run lint:tailwind` to diagnose non-canonical classes and `npm run lint:tailwind:fix` to format them.

## 3. Strict Coding Standards

- **No `any`**: Always provide accurate TypeScript types, discriminated unions, or generics.
- **No `@ts-ignore`**: Banned by ESLint. Use `@ts-expect-error` with a descriptive reason only if strictly unavoidable.
- **No Floating Promises**: Always `await` or properly handle Promises.
- **No Dead Code**: Do not export unused types/functions or leave unused packages in `package.json`. Knip checks this in CI and verification gates.
- **Comments & Naming**: Keep code comments and identifiers concise, professional, and in English.

## 4. Testing Standards (TDD & Spec-Driven)

- Write unit tests under `src/engine/__tests__/` before implementing complex game features.
- Test suites must cover:
  1. 8-direction raycast and boundary conditions.
  2. Multi-team ally/enemy logic.
  3. `WALL` blocking and `PIERCE` penetration.
  4. `COUNTER` reversal mechanics.
  5. `BOMB` 3x3 explosion and recursive chain reaction.
  6. `PURIFY` pulse aura and 3-turn lifespan decay.
  7. Fog of war sanitization for opponent and teammate perspectives.

## 5. Verification Gate (Definition of Done)

The project employs a two-tier verification gate strategy for optimal developer and agent ergonomics:

### Inner Loop: Fast Feedback (`check:fast`)

Use during active coding, iterative refactoring, and debugging (~1s execution time):

```bash
npm run check:fast
```

Runs:

1. `typecheck` (`tsc -b` in strict mode)
2. `lint` (ESLint strict + stylistic type checks)
3. `test` (Vitest unit and integration test suite)

### Outer Loop: Unified Verification Gate (`check`)

Before completing any task, PR, or commit, execute the full Definition of Done:

```bash
npm run check
```

Runs:

1. `typecheck` (`tsc -b` in strict mode)
2. `lint` (ESLint strict + stylistic type checks)
3. `lint:tailwind` (Official Tailwind CSS v4 canonical class check via `@tailwindcss/oxide`)
4. `format:check` (Prettier style validation)
5. `check:deadcode` (Knip unused exports and dependency check)
6. `test` (Vitest unit and integration test suite)
7. `build` (Vite production bundle verification)

All checks must pass with **0 errors and 0 warnings**.
